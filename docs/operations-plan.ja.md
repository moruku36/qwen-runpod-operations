本書は初回試行前に作成した**過去の運用計画**を、検討内容を省略せずに保存したもの。以下の「初回」「推奨」「段階」は当時の計画を示す。予算希望や過去の有料利用承認は履歴であり、追加の起動・再開・削除を承認するものではない。次の試行には新しい計画と必要な承認が必要。

このリポジトリは**公開**であり、mainには試行後に統合した実装も含まれる。実際に実行したコードは[固定commit `69795d54490ffaeff62f18ca80f6181ea674bc16`](https://github.com/moruku36/qwen-runpod-operations/tree/69795d54490ffaeff62f18ca80f6181ea674bc16)を参照する。アカウント固有の残高・決済情報、秘密のURL、実際のPod IDは公開資料に含めない。引用番号は[一次資料一覧](sources.ja.md)に対応する。

## 目的と範囲

既存の Qwen チャット環境を、Colab のコンピュートユニット補充を待たずに使える候補として検証する。判断するのは「起動と終了の手間」「日本語チャットと画像理解の使い心地」「1回の作業セッションの実費」。個人用・単一利用者・非機密のテストデータから始める。

基準は `9e5ff82cf604dd3b0377de81b89e1f4aaa422947` の Q8 チャット Notebook。Gemini会話に出てくる72B/Q4、vLLM、Open WebUIは別の構成で、そちらの速度や費用試算は流用しない。BF16は後日の比較候補とし、モデルも量子化方式も初回には変更しない。[S1–S5]

## 標準の実験サイクル

1. **計画**: 試行IDを付け、目的・仮説・比較条件・合否基準・実行時間・見積・成果の保存先・削除対象の範囲を新しい計画書に記す。前回の結果と差分を明示する
2. **実行**: 当該計画の有料利用承認後に必要なリソースだけ作成する。作成時にリソース種別・ID・名前・関係・作成前から存在したかを台帳に記録する
3. **保存と検証**: レポート、測定結果、非秘密ログ、固定ソース/モデルのSHA・hash、環境/依存lock、再現手順を、今回削除するPod・Volumeの外へ保存する。原則はこの公開GitHubリポジトリに公開してよい非機密資料だけを残し、秘密・生会話・アカウント固有情報を含めない。サイズや機密性等で別の保存先が必要なら受取先・内容・アクセス範囲を先に決める。Pod内のコピーだけでは保存完了にしない
4. **削除確認**: 外部保存先でファイルを実際に開き、必要な結果・再現情報が揃うこと、ファイル数・サイズ・hash等で欠落がないことを確認する。その後、この試行が作成したリソースだけを一覧化し、不可逆削除は正確なID・消えるデータ・影響を示して実行直前に本人の確認を得る
5. **撤収**: 確認した対象だけを削除し、履歴DB、添付、モデル、キャッシュ、ビルド物を含む使い捨て環境を残さない。Pods・Storage・Billingと台帳を照合して実験用の課金対象が残っていないことを確認する。未確認・保留中は撤収完了と扱わない
6. **次の試行**: 前回の環境を暗黙に継続せず、新しい計画書から始める。毎回のcold start、モデル再取得、ビルド時間を見積に戻す

「全部削除」は当該実験のために作成したコンポーネントに限る。既存のアカウント、他のPod/Volume、共有資源、このGitHubリポジトリや保存済みレポートは対象外。初回はAPIキー、Network Volume、独立したテンプレートやイメージ等を必要なく増やさない。例外として作った場合だけ台帳に加え、共有・既存のものと区別して扱う。

履歴DBや生の会話全文を保存すること自体は目的ではない。合否確認後は削除対象とし、再現に必要な非機密テスト入力と匿名化した結果をレポートへ残す。必要なDB/添付を例外的に残す場合は保存先・内容・アクセス範囲を先に確認する。

初稿の時点では計画資料のみで、RunPodリソースは未作成だった。実際の試行と残存リソースは冒頭の2026-10-02更新および試行レポートを参照。計画方針への同意は、入金・有料起動・不可逆削除の実行承認とは別であり、本書は自動実行や自動ハードキャップを有効化しない。

| 項目 | 初回案 | 理由と留意点 |
| --- | --- | --- |
| サービス | RunPod Pods / Secure Cloud / On-Demand | Notebookで段階的に確認できる。初回は中断され得るSpotを避ける |
| GPU | A100 80GB × 1 | 元Notebookの対象。Q8での実測はまだない |
| 代替比較 | A40 48GB × 1 | 安価。重みと投影器の約28GBに対し容量上は余地があるが、速度・長文・画像時の余裕は検証が必要 |
| テンプレート | RunPod公式PyTorch/CUDA開発用イメージを起動時に選定 | Python 3.10以上、Jupyter、nvcc、CMake/Ninja、C++ビルド環境を確認。タグに加えイメージdigestを記録 |
| 試行中の保存領域 | Pod Volume 80GB、`/workspace` | モデル、ビルド成果物、履歴ミラー、実験記録を当該試行中だけ保持。Terminateで消失するため成果は事前に外部へ保存・検証 |
| Container Disk | 20GBを計画値とし、選択テンプレートの必要容量で調整 | OS側の一時領域。停止・再作成に耐える保存先とは考えない |
| CPU / RAM | 8 vCPU、RAM64GB以上を計画上の目安 | ビルドとCPU ASRの余裕。保証された最小要件ではなく、実際の割当と最大RSSを記録 |
| 入口 | 認証されたJupyterとGradio | `SHARE=False`。無認証URLを外部公開しない |
| 推論 | 同じPod内のllama.cpp | 既存のGGUF/mmprojをそのまま使い、vLLM移行を同時に行わない |
| 初回時間 | 最大2時間の有人セッション | 構築、ダウンロード、確認、終了まで全て含む。費用上限は起動前に承認する |

**標準は1回ごとに使い捨てるPod Volume案**。成果を外部へ保存・検証し、対象別の削除確認を得てからPodをTerminateする。Network Volume 80GBを7日保持する案は将来の比較用の非標準オプションとしてのみ残す。短期間に複数試行を行う場合、保持費用と毎回の再取得・再ビルドにかかるGPU費を比べ、新しい計画で明示的に選ぶまでは作成しない。[S8–S12]

## ストレージ設計

80GBは測定済み必要量ではなく、約28GBの重み、Python環境・ASR・ビルド用10–20GB、ログ・テスト・履歴用数GB、ダウンロード途中と将来の余裕を見た計画容量。全モデルリポジトリを丸ごとダウンロードしない。GGUFとmmprojの指定ファイルだけを取得する。HFキャッシュと手動コピーでモデルを二重保持しない。未取得モデルの合計サイズ＋20GB以上の空きを初回ダウンロード前の目安とし、重み取得後も実使用量を記録する。

| 保存先 | 内容 | 消失・保全の扱い |
| --- | --- | --- |
| `/workspace/qwen/source` | 固定SHAのソース | 再取得できるが、未保存変更を残さない |
| `/workspace/qwen/hf-cache` | 指定したモデル2ファイルとASRキャッシュ | 当該Pod Volume内だけで再利用。試行後に削除し、次回は再取得時間も見積もる |
| `/workspace/qwen/llama-bin` | CUDAアーキテクチャ別ビルド成果物 | 試行後に削除。commit、CUDA、GPU arch、イメージdigest、ビルド手順を外部のレポートに保存 |
| `/workspace/qwen/data` | 履歴DBのミラーと添付 | Git対象外。非機密テストのみとし、必要な結果をレポート化した後、確認した対象として削除 |
| `/tmp/qmc/history.db` | 実行中SQLiteのローカル作業DB | 終了前にミラー同期と読み戻しを確認。永続化済みとはみなさない |
| `/workspace/qwen/runs` | 計測・依存バージョン・停止確認 | 一時保存。秘密と生会話を除く結果を外部リポジトリに保存し、読み戻し検証してからPodを削除 |

公式のstorage設定では保存時暗号化の選択機能はPod Volume向けで、Network Volumeには同機能を適用できない。Network Volumeを機密保管庫として扱わず、個人・業務の機密データを入れる場合は別途暗号化と保管先を設計する。[S10]

ネットワークファイルシステム上のSQLiteを直接運用する変更は初回に入れない。現行のローカルDB＋ミラー構成を維持し、強制終了時には最後の同期後のデータが失われる可能性を許容できる非機密テストに限定する。[S3]

## 費用の試算（過去の計画値）

以下はUSD、税・カード手数料・為替差・外部検索API料金を含まない計画値。ストレージ月額の按分は比較用に1か月720時間として計算した。請求側の月換算・端数処理と完全に一致する保証はない。

公開値: Container Disk $0.10/GB/月（稼働中）、Pod Volume $0.10/GB/月（稼働中）・$0.20/GB/月（停止中）、標準Network Volumeは1TB未満で$0.07/GB/月。高性能ストレージ等の別ティアはこの表に含めない。[S9–S12]

計算式:

標準のPod Volume案:

`概算 = GPU単価 × 割当時間 + Container GB × 0.10 × 稼働時間/720 + Pod Volume GB × (0.10 × 稼働時間 + 0.20 × 停止時間)/720`

A100を2時間使い、停止保持時間0時間で撤収できた場合: `1.59 × 2 + 20 × 0.10 × 2/720 + 80 × 0.10 × 2/720 = 3.2078 USD ≈ $3.21`。

非標準のNetwork Volume案ではPod Volume項を外し、`Network GB × 0.07 × 保持時間/720`を加える。Stopで削除確認待ちに入った場合のPod Volume保持費は別途発生する。

| 利用例 | GPU費 | ディスク等 | 概算合計 |
| --- | ---: | ---: | ---: |
| **標準: 初回A100、2時間、Pod Volume80GB＋Container20GB、保存検証・削除確認後すぐTerminate** | $3.18 | 約$0.03 | **約$3.21** |
| 次の新計画でA40、2時間、同容量のPod Volume＋Containerを新規作成し撤収 | $0.98 | 約$0.03 | 約$1.01。新規構築・取得時間も2時間に含む |
| 非標準比較: A100、2時間、80GB Networkを7日保持、Container20GB | $3.18 | $1.31＋$0.01未満 | 約$4.49 |
| 非標準比較: 月20時間A40、80GB Networkを1か月保持 | $9.80 | $5.60＋約$0.06 | 約$15.46/月 |
| 非標準比較: 月20時間A100、80GB Networkを1か月保持 | $31.80 | $5.60＋約$0.06 | 約$37.46/月 |
| GPU未使用でNetwork80GBを1か月残す | $0 | $5.60 | $5.60/月 |
| GPU未使用でPod Volume80GBのPodを1か月Stopのまま残す | $0 | $16.00 | $16.00/月 |
| A100を24時間止め忘れる | $38.16 | 別途ディスク費 | $38.16超 |

当初は全体で約$10に収めたいという予算希望を前提に、初回は最大2時間・概算$3.21を基準にした。これは当時の計画値であり、後の試行の実費や今後の支出承認を示さない。ただし約$10は支出承認でも自動ハードキャップでもない。試行ごとの総額上限（税・手数料、保存確認・削除待ちの費用を含む）、入金額、実行日を起動前に確定・承認する。残額や料金だけから次の試行を自動で追加しない。プリペイド入金額はサービス消費額と別。公式Billingガイドは$10からの入金と、クレジットの返金・出金不可を案内している。最低入金額・返金条件・自動補充の有無は決済画面でも確認してから承認する。残高ゼロを終了装置に使わない。停止・データ消失につながる可能性がある。

RunPod PodsではGPUが稼働している間、起動・回答待ち・入力中・ビルド・ダウンロード・結果の回収も課金対象。使い捨て運用では次の試行でこれらをやり直すため、2時間は推論だけの持ち時間ではない。1問の生成秒数だけに単価を掛けた値は、実際の利用料にならない。Serverlessも初期化やidle timeout等を含むので「推論の数秒だけ」と断言しない。[S9,S16]

## Colabと比べる方法

- RunPodの利点: GPU/ディスク/イメージを選び、固定した設定で環境を作り直しやすい。標準運用では使わない期間の実験用保存費用を残さない
- 使い捨てのトレードオフ: 毎回の起動・モデル取得・ビルドにGPU費と時間がかかる。連続試行では短期保持より必ず安いとは限らず、前回の実測で次の計画の見積を更新する
- RunPodの負担: 初回移植、認証・ポート管理、保存費用、起動停止確認、GPU在庫が必要。元Notebookを無変更で開くだけの簡単さではない
- Colabの利点: 既存のNotebook、Secrets、Drive連携を利用しやすい。既に含まれる未使用CUがあれば追加支出を抑えられる場合がある
- Colabの制約: GPUの種類・割当や利用制限は変動し、購入したCUもGPU在庫を保証しない。既存ロードマップの10月23日以降の検証予定は、この計画だけで変更しない

公平な比較は、同じモデル・ハッシュ・llama.cpp・入力・コンテキスト・出力上限で「起動から安全な終了までの請求額」を測ること。Colabの実効費用は「購入時の単価/CU × そのセッションの実消費CU」で求める。既契約分をどう按分するかも併記する。

Colab購入ページの価格は地域・通貨で異なる。調査ブラウザではGBP表示だったため、日本アカウントの現在価格やUSD価格として転用しない。Gemini会話の「A100で毎時10–15CU」「$9.99で100CU」は今回のアカウント実測・見積ではない。[S17–S18]

## アクセスと秘密情報

1. 初回はRunPod管理画面から認証付きJupyterへ接続。Gradioにも専用認証を設定し、ログアウト状態から会話・履歴・ファイル・APIにアクセスできないことを確認する
2. HTTP proxyはHTTPS経路であって、URLを知る人を自動で認証する仕組みと同一視しない。未認証の7860/8888を開放しない
3. llama-serverは現行どおり`127.0.0.1:8012`と起動ごとのAPI keyを維持し、外部公開しない。外部API連携は後工程にする
4. `SHARE=False`、`QMC_SHARE=false`。`gradio.live`等の公開トンネルを初回に使わない。SSHを選ぶ場合は管理画面の公開鍵・正式接続手順に従い、ポートを必要最小限にする
5. GitHub token、RunPod account API keyは初回Notebookに渡さない。公開の元ソースを固定SHAで取得できるため不要
6. HFモデルが公開取得できるならHF_TOKENを入れない。必要になった場合だけ目的と権限を確認し、RunPod Secrets等の秘密保存に渡す。秘密の値をNotebook、ログ、`.env.example`、GitHub、画面キャプチャに残さない
7. 初回のローカルモデル確認ではWeb検索をOffにし、次に非機密の検索クエリで確認する。検索は第三者にクエリが送信される。TTSはOffのまま、CPU ASRは自作音声で試す

現行`AppConfig.public_dict()`は`auth_password`とremote API keyを除外する一方、`github_token`全体を除外する実装ではない。実験情報の出力にその辞書や環境変数全体を使わず、GPU・バージョン・非秘密設定の許可リストで記録する。[S3,S13–S15]

## 終了と課金の区別

| 操作 | GPU課金 | データの扱い |
| --- | --- | --- |
| ブラウザを閉じる、UIのStop、Release GPU model | 止まらない | Podは稼働を続け得る |
| `colab.shutdown_runtime()`をRunPodで呼ぶ | 止まらない | アプリ終了のみ。RunPodを停止する処理がない |
| RunPod管理画面でStop | 計算資源の課金を停止 | Container Diskは破棄、Pod VolumeまたはNetwork Volumeは残り保存費用が続く。Container上の必要データを先に外部保存し、不可逆消失を伴う実行は対象確認を行う |
| RunPod管理画面でTerminate | そのPodの計算資源を終了 | Container/Pod Volumeは失われる。外部保存検証後、Pod IDと消えるデータを示して実行直前の削除確認が必要。独立したNetwork Volumeは残り、課金も残る |
| 独立Network Volumeも削除 | 当該保存費用を終了 | 標準では作成しない。例外として当該実験で作成した対象のみ、外部保存検証と実行直前の対象別削除確認が必要 |

現行公式ガイドではNetwork Volume付きPodもStopまたはTerminateの双方を説明している。古い「Network Volume付きPodはStopできない」という説明に依存しない。実際の管理画面、Pod状態、課金欄で結果を確認する。StopしたPodは同じGPUが空かず再開できない場合がある。Network Volumeがあれば同一データセンターの互換GPUへ再作成する余地があるが、在庫は保証されない。[S10–S12]

## 自動終了を入れる順番

最初は有人セッション＋別の時計で終了時刻を確認し、管理画面で停止する。Notebook末尾の`time.sleep(300)`だけでは、途中例外・カーネル停止・ブラウザ切断・利用再開に対応できず、5分後のデータ削除も危険。

自動化するなら次の実装段階で設計する。

- セッションの最大経過時間と、最後の処理完了後のidle時間を分ける
- 推論中、書き込み中、利用再開時はidle終了を延期する
- 原則は先に必要データを使い捨て環境の外へ保存・検証する。StopでもContainerの消失に注意する。TerminateやVolume削除のような不可逆操作は対象IDと消えるデータを示し、実行直前の本人確認を受けてから行う。計画時の一括同意で自動削除しない
- Notebookプロセスが死んでも機能する監視を検討する。終了APIの成功とPod状態を外部から確認する
- 管理API keyの権限・保持先・失効方法を決め、必要なアクセス作成は別途承認する。フル権限のaccount keyをNotebookへ直書きしない
- 自動終了は初回の受け入れ条件にはせず、手動終了の確実さを先に証明する

## 段階と判断

1. 計画: 初稿で扱った段階。ソース、モデル、費用、停止手順を確認
2. 無課金の移植準備: 新Notebookの入口、パス、認証、依存ロック、chat-only測定を作り、CPUテストを行う。元リポジトリの書換えは別途扱う
3. 初回A100: 試行計画・総支出上限・成果の外部保存先・実行日を確定し、有料利用の承認後に起動。テキスト、画像、検索、ASR、履歴、再起動、停止課金を記録
4. レポートと撤収: 結果・再現情報を外部へ保存して読み戻し検証し、当該実験リソースの台帳と削除対象を照合。実行直前の削除確認後に撤収し、残存課金対象を確認
5. 次の計画: 前回の結果と実費を受けて新しい計画書を作る。A40比較を行うなら同じモデル・条件で評価する別の試行として予算・再構築時間を見積もる。追加起動は新計画の承認後
6. 継続判断: セッション単価、操作時間、回答の満足度でColab継続・RunPod併用を決める。数問ずつ散発利用なら、cold startを測ってからServerlessを別案件で検討

GPUテスト完了の条件と失敗時の扱いは[チェックリスト](session-checklist.ja.md)を使う。未測定値を成功として埋めない。
