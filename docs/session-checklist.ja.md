# セッション実施チェックリスト

このチェックリストは将来の有料試行用。すべて未実施で開始し、担当者が確認したものだけチェックする。

## 起動前

- [ ] 実行日、最大2時間などの終了時刻、USD総支出上限、税・手数料、保存期間を本人が承認
- [ ] RunPodのアカウント、支払方法、入金額、返金条件、自動補充の有無を確認。新しい契約やアクセス作成が必要なら別途承認
- [ ] 元ソースSHA、Notebook blob、モデルファイル名・hashを記録
- [ ] RunPod対応入口と依存lockの準備を終え、CPUテストを確認
- [ ] Secure Cloud On-Demand、GPU1台、実際の単価、データセンター、RAM、ディスク種類/容量を確認
- [ ] Network Volumeを使う場合は、その場所で対象GPUの在庫を先に確認
- [ ] Jupyter・Gradioの認証を有効化。秘密の入力は適切な秘密管理手段で行う
- [ ] テスト用の非機密プロンプト、自作画像、短い自作音声を先に用意
- [ ] 作業時間をGPU上で計画しない。終了用の時計・手順を手元に用意

## 起動直後

- [ ] Pod ID、起動時刻、価格、template/image digestを記録。秘密を含むURLや画面は記録しない
- [ ] `nvidia-smi`でGPU名・VRAM・driverを確認。想定外のGPUならモデル取得前に停止判断
- [ ] CUDA toolkit/ビルドツール/Pythonが揃い、`/workspace`が意図した保存領域であることを確認
- [ ] 未取得モデルの合計サイズ＋20GBを目安とする空きがあり、ダウンロード先の二重コピーがない
- [ ] 未ログイン状態でJupyter/Gradioの会話・履歴・添付が見えない。llama-server8012は外部公開されていない
- [ ] モデル2ファイルを固定revisionで取得しSHA256照合。全HFリポジトリはダウンロードしない

## 機能と測定

- [ ] 8k、検索Off、thinkingOffの短文で最初の応答が出る
- [ ] 同じ10個の日本語プロンプトを実行し、初回token時間・完了時間・出力token数を記録
- [ ] 画像1枚の既知の内容が正しく説明できる。元画像を履歴に保持して再表示できる
- [ ] 32kへ上げた別試行を記録。OOM/自動縮退/CPU offloadの有無を隠さない
- [ ] 複数画像や長めの会話、連続10ターンでエラーとメモリ増加を確認
- [ ] 非機密クエリで検索Onを検証。引用・取得失敗の扱いを確認
- [ ] 10–20秒の自作日本語音声でCPU ASRを確認。マイクはHTTPS経由で本人の許可を確認
- [ ] Stop、Regenerate、Release GPU model、再ロード、launchセル再実行で二重プロセス・二重VRAM・ポート衝突がない
- [ ] 履歴同期後にアプリ再起動で戻ることを確認。初回が成功したら新規Pod＋同じvolumeで再現も確認
- [ ] GPU課金時間はモデル推論時間ではなく、起動からStop/Terminate確認まで記録

## 合格の判断

必須条件は、認証漏れ・秘密漏れがないこと、意図したモデルでチャットと画像理解が完了すること、履歴が復元できること、停止操作でGPU課金を止められること。致命的なエラーやOOMを残したまま継続運用にしない。

使い心地の仮基準として、warm・短文・検索Off・thinkingOffの10試行で初回tokenの中央値5秒以内、最大256 output tokenの完了中央値30秒以内を置く。これは性能予測でも保証でもなく、使えるか判断するための提案基準。実行前に調整可。画像・検索・ASRとcold startは別枠で評価する。

A40採用は同じ条件で必須条件を満たし、回答の満足度が許容範囲で、起動から終了までの費用がA100より低いこと。単に時給が安いだけでは採用しない。

## 異常時と戻し方

- 予算/時間上限到達、認証の欠落、秘密漏れ: 新規処理を中断し、必要データを保存、PodをStop。公開設定を直す前に利用を続けない
- OOM: 並列を1、画像1枚、8kへ戻し、縮退したことを記録。A40で再発するならA100へ戻す。Q4へ勝手に変えない
- 起動不可/依存不整合: 固定SHAとimage/lockへ戻す。ライブラリを総当たり更新しながらGPUを放置しない
- 検索サービス停止: モデル単体試験を続けてよいが検索を合格にしない
- volume I/O/同期失敗: Terminateしない。復旧可能なデータを保存し、Stop後の回収方法を確認する
- 在庫不足: 別GPUを無断で購入しない。volumeのデータセンター制約を踏まえ、延期か再見積
- 元Colabへ戻す場合: 元Notebookと元リポジトリは変更していないため、そのまま既存手順を利用。RunPodの残存volumeと料金を別に整理

## 毎回の終了

1. [ ] 新規送信を止め、実行中処理が完了/取消済みであることを確認
2. [ ] 履歴・添付を同期し、計測記録を保存。必要なDB/ファイルの読み戻し確認を行う
3. [ ] アプリ・モデルを終了。ただし、この時点ではGPU課金は止まったと扱わない
4. [ ] RunPod管理画面でStop、または承認した使い捨てPodをTerminate
5. [ ] 管理画面にStopped/削除済みが表示され、GPUの継続課金対象が残っていないことを確認。停止時刻を記録
6. [ ] 残存するPod Volume/Network Volume名、容量、月額、保存期限を記録
7. [ ] セッション実費をBillingと照合。反映が遅ければ「未確定」と記す

## 試行を終了するとき

- [ ] 継続利用か完全撤収かを決める
- [ ] 必要なバックアップをRunPod外へ回収し、復元できることを確認
- [ ] 不要なPodはTerminate。不可逆削除対象と影響を確認する
- [ ] 不要Network Volumeは別途削除承認後に削除。Pod削除だけで無料化されたと思い込まない
- [ ] 一時的に作成したキー・アクセスを必要に応じ失効し、秘密を含むNotebook出力やログを整理
- [ ] Pods・Storage・Billingで継続課金対象が残っていないことを確認して完了
