- Image digest: `rcr.runpod.io/runpod/pytorch@sha256:61a4aafb0094cd773f11eefa378929d5a687bd775febeb78eac62fc824141fb5`, tag `runpod/pytorch:2.4.0-py3.11-cuda12.4.1-devel-ubuntu22.04`. This supports the first Pod's `image_digest`; it is not an independently retrieved digest for the second Pod or its restarted session
- A system log line said “create 80GB network volume.” The console's Volume rate matched Pod Volume pricing, so this record treats it as a Pod Volume while preserving the wording
- At creation, the API's `dataCenterId` was `US-MD-1`. Its displayed properties were `globalNetwork: false`, without compliance or networkVolumeTypes information

## Second trial record

- GPU operation lasted approximately 14:50–15:19, about 29 minutes, approximately $0.77. Together with the first trial, GPU cost was approximately $0.97 at that point. Both Volumes continued to incur approximately $0.022/hour each. Both Pods were stopped; neither was terminated
- **Not performed at this stage:** CUDA compilation, downloading and hashing complete model files, model loading, inference, UI checks, and production trial-report generation. Intermediate `/workspace` contents, including the clone and `isolated-*`, remained
- **What changed from the first trial:** the No route to host error did not recur in `EUR-IS-1`. A `US-MD-1`-specific or temporary routing problem is an inference; the cause was not established

## Causes and responses

1. **`pip check` failed because of OS packages in system Python, PyGObject → pycairo, rather than this project's dependencies.** Installing directly into system Python and checking that environment was the wrong procedure. The implementation was changed to install into `/workspace/qwen/venv`, without system site-packages, and run `pip check` only there using `scripts/pod_run.py venv`
2. **The 240-second cutoff was observed.** At this stage, completion time on the Pod was unknown; the development environment took approximately 39 seconds. The procedure was changed to run in the background without that time limit, writing progress to logs. A later installation succeeded in approximately 297 seconds, demonstrating that 240 seconds was shorter than that observed duration. Because it was a separate run, this does not establish that the earlier attempt would certainly have succeeded if allowed to continue
3. To handle **venv-creation failure** when system Python lacks ensurepip, a fallback was added: create the venv with `--without-pip`, then pass `--python` to the host's pip. **Whether this failure would occur on the Pod had not yet been checked**

4. The cause of the first trial's No route to host error

## Third trial record

- **The log route worked.** Lines written to PID 1's standard output and an artifact with a matching SHA256 reached the container logs. Claude could receive progress and small artifacts without a person relaying them. This did not enable arbitrary command execution
- **About the earlier 240-second cutoff:** the earlier procedure was interrupted at 240 seconds, whereas this attempt without that limit completed installation in approximately 297 seconds. This supports the explanation that the earlier limit was too short
- **Kernel registration was confirmed separately from successful venv installation.** The code prints `state=ok kernel=qwen-venv` without checking the registration command's exit code, so that line alone is not evidence. A separate `KernelSpecManager` check found it present. Appearance in Jupyter's visible kernel list was not checked
- Only selftest, net, and venv ran. `source`, `build`, `trial`, and `all` did not run
- The first Pod remained stopped at this point. No Terminate. See the next section for the second Pod's final stop state
